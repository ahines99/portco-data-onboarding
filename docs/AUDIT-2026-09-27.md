## Assessment

This is a working, substantial deterministic onboarding MVP, with a functioning local demo and extensive automated coverage. It is **not acceptance-complete or ready for production data**. The earlier claim that all implementation work is finished and only user actions remain is not supported by this audit.

The existing checks all pass, but targeted reproductions exposed five high-priority defects in schema authorization, approval enforcement, publication recovery, metric certification, and SQLite audit concurrency. Additional privacy, configuration, packaging, and evaluation issues remain. Passing the current suite demonstrates its covered behavior; it does not resolve these new findings.

The repository was clean at audit start. No application code, tests, settings, or dependencies were changed in the working repository. This report is the audit deliverable; test/demo/eval commands also generated ignored runtime artifacts. Nothing was committed or pushed. No Git remote is configured.

## Audit method and scope

The requested five distinct agents could not be created: the runtime enforces a four-thread limit including the lead, and rejected new agents even after existing auditors completed. Three specialist agents plus the lead conducted five focused passes, with two specialists reused for the final scopes:

1. Security, privacy, MCP authorization, tenant and source boundaries.
2. Workflow, persistence, concurrency, approvals, sandbox, and publication.
3. Independent tests, static checks, evaluation, demo, and clean-checkout verification.
4. Roadmap, handoff, acceptance claims, documentation, and operational readiness.
5. Evaluation rigor and data/semantic correctness.

The lead additionally checked packaging, example configuration, schema/document drift, repository history, and completion claims. The pasted prior conversation was treated as historical context; current source and freshly executed checks take precedence.

Evidence labels used below:

- **Reproduced:** executed a focused check demonstrating the failure.
- **Traced:** established the code path or missing control by inspection; no end-to-end failure reproduction.
- **Unverified:** implementation exists, but execution evidence was unavailable.
- **Deferred:** explicitly outside the v0.1 scope.

This is a source and behavioral audit, not a complete dependency-vulnerability scan, production penetration test, load test, or proof that no other defects exist.

## High-priority findings

### F01 — Caller-selected schemas bypass a registered connection's allowlist

**High; reproduced through the real service facade.** Location: [external.py](../src/adapters/external.py), line 500.

`ConnectionRegistry.resolve()` replaces a registered connection's schema restrictions with the caller's `?schemas=` value. A company-scoped agent used a connection registered with `schemas=['allowed']`, supplied `?schemas=secret`, and obtained a profile of `secret.salary`, including minimum `12345`. An empty schema selection also becomes unrestricted because the adapter treats an empty list as all nonsystem schemas.

This requires a restricted operator-registered connection; the stock configuration exposes fixture connections and has no MCP registration tool. Company authorization remains enforced, but does not protect schemas excluded by the operator within an authorized connection.

**Work:** enforce requested schemas as a subset of the registered allowlist; preserve restrictions for empty requests. Add facade/MCP tests for widening, empty selection, unknown schemas, and legitimate narrowing.

### F02 — Ordinary approval applies an override that bypasses validation

**High; reproduced.** Locations: [approvals.py](../src/services/approvals.py), line 51; [gates.py](../src/services/gates.py), line 102.

Override validation runs only for `approve_with_override`, but mapping resolution applies the override payload for ordinary `approve` too. An item requiring `pii_handling='exclude'` accepted `decision='approve', override={'pii_handling':'hash'}` and resolved to hashing with `overridden=False`.

Reviewer credentials are still required; this is a policy-validation bypass, not an agent gaining reviewer privileges. It violates the accepted rule that PII handling can only become stricter and misreports the override in audit summaries.

**Work:** reject override payloads for other decision types; validate again before applying them; derive override reporting from actual changes. Cover every decision/payload combination, allowed fields, transforms, and PII strictness.

### F03 — Failed publication can later report success for a missing directory

**High; reproduced.** Locations: [publish.py](../src/services/publish.py), lines 70, 160 and 173.

The database publication receipt commits before the staging directory is renamed into place. A forced rename failure left the receipt committed. On retry, publication returned `reused=True` even though the receipt's destination did not exist. Concurrent callers can likewise observe the receipt before materialization finishes.

**Work:** model publication as a recoverable lifecycle, persist staging/finalization state, verify filesystem content before receipt reuse, and recover interrupted operations. Test failures at each database/filesystem boundary. Simply swapping insert and rename order creates a different crash window.

### F04 — Concurrent SQLite audit appends break the integrity chain

**High; reproduced.** Location: [repositories.py](../src/adapters/repositories.py), line 358.

Two transactions can read the same chain head because SQLite does not provide the intended row lock for `FOR UPDATE`. Both subsequently commit events using that head. A two-thread reproduction synchronized the inserts, obtained two successful commits, then returned `verify_chain=False`, with the chain broken at event 2.

Run execution leases do not serialize every audit writer: MCP accounting and policy-denial events also append independently.

**Work:** acquire the SQLite write lock before reading the head, or implement an atomic compare-and-swap protocol with retries. Retain the appropriate Postgres locking path. Add concurrent append tests rather than only tampering/deletion tests.

### F05 — Publication does not revalidate every metric certification

**High; reproduced.** Location: [publish.py](../src/services/publish.py), line 35.

Publish checks a valid accepted bundle approval and a nonempty `packet.certification_ids`. It does not ensure that each included metric still has a valid effective approval. A reproduction supplied a valid bundle approval plus an expired separate approval for `metric:billings`; billings was still published.

This can arise when approvals are submitted separately and execution pauses between certification and publication, allowing an older metric approval to expire while the bundle approval remains valid.

**Work:** reload and validate all required approvals at publication; recompute effective per-item decisions; compare them with the packet's published/excluded metric set. Cover expiration and revocation of separate approvals, not only the bundle approval.
