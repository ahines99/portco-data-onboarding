# Repository audit — 2026-10-10

Audited source: [`e1f8e36936f832b019dbd9418994ea95dc47f7a5`](https://github.com/ahines99/portco-data-onboarding/commit/e1f8e36936f832b019dbd9418994ea95dc47f7a5), also the remote `main` observed during this audit. The working tree was clean at the start. Application code was not changed by this audit.

Ten specialist agents reviewed the project in batches of three, with a coordinating agent running verification, checking reproductions and consolidating findings. This report separates reproduced defects, source-supported risks, measurements and recommendations. It is an engineering audit of the checked-out project, not a certification of all possible inputs or a live penetration test.

## Assessment

This is a substantial, reproducible portfolio prototype with unusually good evidence discipline: typed MCP interfaces, independent financial calculations, reviewer separation, content-bound approvals, transactional audit records, publication recovery, real PostgreSQL integration, and installation/container CI. Its documentation generally distinguishes synthetic and agent-operated evidence from human/customer validation.

The next release should focus on correctness at the boundaries between those mechanisms. Passing tests currently coexist with incorrect financial classification, unapproved relationships, cached authorization checks and stale-worker authority. Those are higher-value fixes than expanding the connector list or deploying a backend.

The most important reproduced findings are:

1. A source account type of `Revenue` can turn a 100.00 revenue credit into **0.00 recognized revenue and EBITDA**, with dbt and all reconciliation checks passing.
2. A reviewer-rejected GL-account relationship is recreated by the generated mart, while the certification packet lists no accepted join.
3. Unrelated tables with overlapping generic integer IDs can receive unreviewed, high-confidence joins. A vendor deletion filter then removes an unrelated customer from generated output.
4. Artifact-generation cache reuse can skip the current mapping-approval check after revocation.
5. A worker resuming after lease takeover can adopt its successor's lease identity and finalize publication before its own result is rejected.

These findings do not establish a JWT bypass, an agent's ability to grant itself reviewer authority, or publication without a separate certification. They do establish failures in the project's stated relationship, approval and execution guarantees.

## Highest-priority correctness fixes

`P1` means fix before broadening inputs or relying on this behavior for consequential use. `P2` means a concrete bounded defect or important reliability improvement. `P3` means maintenance, evidence or usability work. These are engineering priorities, not CVSS scores. Specialist notes sometimes use a deployment-specific priority; the ordering here is the consolidated recommendation.

### A01 — P1: validate canonical financial categories before calculating money

**Evidence:** A synthetic journal line with a 100.00 credit and source `account_type='Revenue'` passed an actual generated dbt build and eight reconciliation checks, producing zero recognized revenue and EBITDA. Generated accepted-values tests repeat the source-approved labels, while SQL and Python calculators recognize only lowercase canonical labels. Both implementations therefore make the same semantic omission.

**Locations:** [generation.py:264](../src/services/generation.py#L264), [metrics_reference.py:257](../src/domain/metrics_reference.py#L257), [sandbox.py:502](../src/services/sandbox.py#L502), [ontology definition](../ontology/pe_canonical_v1.yaml).

**Fix:** Make canonical category constraints executable contracts. Count unknown/null classifications independently of whether category labels are permitted to leave the adapter. Block affected metrics until an explicit normalization or reviewed source-to-canonical crosswalk exists. An approved category disclosure domain does not establish accounting meaning.

**Acceptance:** `Revenue`, unknown ERP codes, whitespace variants and null classifications cannot produce passing zero metrics without an explicit supported mapping. Valid balance-sheet categories still contribute legitimate zero revenue. Keep independent arithmetic and add independent semantic expectations. dbt's [`accepted_values` test](https://docs.getdbt.com/reference/resource-properties/data-tests) validates only the supplied list; choosing that list correctly is the application's responsibility.

### A02 — P1: honor rejected relationships throughout generation and certification

**Evidence:** Resolving an explicit rejection removes the GL-entry/account join and retains its rejected key. `Generator.build_marts()` then adds the ontology lookup anyway. Actual dbt execution and eight reconciliation checks pass. The generated SQL joins the tables, but certification takes its join list from the empty resolved list. The probe executed resolution, generation and sandbox checks; later publication copying is source-traced, not separately executed in this probe.

**Locations:** [generation.py:385](../src/services/generation.py#L385), [gates.py:167](../src/services/gates.py#L167), [certification.py:74](../src/services/certification.py#L74).

**Fix:** Require every ontology lookup to match an accepted source relationship, including endpoints, fields and supported cardinality. When that evidence is absent or rejected, withhold dependent metrics as `NEEDS_EVIDENCE`. Reconciliation must honor the same approval contract while calculating values independently. Certification must describe every relationship actually used.

**Acceptance:** Rejecting a relationship removes its influence from generated SQL and reference expectations. Test both explicit rejection and absence of an inferred relationship.

### A03 — P1: overlapping generic IDs are insufficient evidence for automatic joins

**Evidence:** Real inference over unrelated customer/vendor tables with IDs 1–3 produces two joins scored 1.0/HIGH without review, despite LOW/MEDIUM entity confidence. The joins survive mapping resolution without join approvals. Executing generated SQL with an approved vendor deletion filter removes customer `Acme` solely because its independent ID matches the deleted vendor's ID.

**Locations:** [joins.py:42](../src/services/joins.py#L42), particularly the own-primary-key/same-field candidate exception at :83 and structural-review decision at :111; [gates.py:167](../src/services/gates.py#L167).

**Fix:** Reject or require review for generic primary-key-to-primary-key matches without semantic or declared relationship evidence. Propagate uncertainty in entity assignment to dependent joins, and handle similarly supported targets as ambiguity rather than arbitrary certainty. Consider validated source FK metadata or explicit source relationship contracts as stronger evidence.

**Acceptance:** Independent surrogate-key sequences must not automatically propagate filters or enrichments between entities. Cover repeated `id` columns, equal containment across several targets, uncertain entities, and approved versus rejected relationships.

### A04 — P1: check authorization before accepting cached generation

**Evidence:** After generating artifacts, the isolated service probe revoked the persisted mapping approval and called public `rerun_from(ARTIFACT_GENERATION)`. Direct generation raised `ApprovalRequired`; the workflow reused the old successful step and advanced to automated tests. The resolved-mapping content hash excludes approval IDs, and cache reuse returns before the generation function checks authority.

**Locations:** [base.py:291](../src/workflows/base.py#L291), [primary.py:46](../src/workflows/primary.py#L46), [generation.py:639](../src/services/generation.py#L639), [project_models.py:308](../src/domain/project_models.py#L308).

**Fix:** Separate current authorization/preconditions from deterministic output computation. Revalidate them before cache acceptance. Adding approval IDs to a hash alone cannot handle time-based expiry.

**Acceptance:** Warm-cache reruns after revocation and expiry stop or return to review. Still-valid equivalent approvals retain safe output reuse. Exercise the public facade/MCP path, not only the generation helper.

### A05 — P1: preserve the original worker's execution identity

**Evidence:** In an actual `engine.run` reproduction, worker A renews, is notionally paused beyond expiry, worker B claims, and A resumes before loading step context. `_run_step` reads B's lease owner into A's context. Publication trusts that value and completes; only the later result persistence recognizes A as stale. The scheduling boundary was injected deterministically rather than waiting through the lease duration.

**Locations:** [base.py:284](../src/workflows/base.py#L284), [contracts.py:48](../src/workflows/contracts.py#L48), [publish.py:267](../src/services/publish.py#L267).

**Fix:** Carry A's original immutable claim token into every context and side-effect check. Lock and verify ownership before starting, reusing or advancing a step; fence publication against that original token. Audit stop-after and failure transitions for the same requirement.

**Acceptance:** Barrier-controlled takeover tests on SQLite and PostgreSQL must prove the stale worker cannot publish, mutate its successor's cursor, pause the successor or release its lease. The successor must still finish exactly once.

## Performance: what to improve and what the measurements support

Measurements used Windows 11, Python 3.12.10 and DuckDB 1.5.5 while other audit/test work ran on the same machine. They are small synthetic/shared-host observations, not production benchmarks. No remote database latency or maximum-size end-to-end capacity was measured.

| Priority | Evidence | Recommended change |
| --- | --- | --- |
| First for remote extraction | Named PostgreSQL cursor calls `fetchone()` once per row at [postgres_source.py:260](../src/adapters/postgres_source.py#L260). Installed Psycopg issues `FETCH FORWARD 1`; 100k rows at 10 ms RTT has a calculated network floor of about 1,000 s versus a 120 s default budget. | Fetch bounded batches. Derive batch size from the 1 MiB per-row ceiling, preserve per-row byte/deadline checks and measure with controlled latency. Setting `itersize` alone does not fix a `fetchone()` loop. [Psycopg cursor documentation](https://www.psycopg.org/psycopg3/docs/api/cursors.html#the-servercursor-class). |
| First for responsiveness | A 350 ms SQLite writer hold caused a 432 ms asynchronous heartbeat gap. Async handlers invoke synchronous transactions; all SQLite `Store.tx()` calls acquire `BEGIN IMMEDIATE`, including reads. | Offload whole transaction units into a bounded pool or adopt async persistence; introduce genuine read transactions while preserving writer/audit locking. Do not move an open SQLAlchemy connection between threads. Test concurrent health/status during blocked database work. |
| Next for ingestion throughput | The unmodified importer took **42.129 s for 20,000 rows / 677,801 CSV bytes**. Row insertion kernels took 42.9–45.8 s. | Benchmark a native typed bulk-loading path after preserving exact validation and private staging. DuckDB [discourages large `executemany` loads](https://duckdb.org/docs/lts/clients/python/dbapi). Python-list `UNNEST` improved only about 1.25x at 20k; it is not an established solution. |
| Next for bounded resource use | `_cols` over 50k rows × eight short strings peaked at 40,001,288 Python bytes, excluding DuckDB and later record copies. Subscription references repeatedly scan subscriptions for every month, with no explicit horizon limit. | Stream/batch reference aggregation, share bounded intermediate calculations, and enforce supported date/horizon budgets. Configure DuckDB memory/threads/temp storage and separately bound Python allocations. Preserve arithmetic independence. |
| Lower priority, with correctness care | Cached 32 MiB hashing took 18–24 ms, but repeats inside async/write-transaction bookkeeping. Eight pattern queries combined into one produced essentially unchanged ~236 ms latency. | Resolve verified source identity outside write transactions; instrument repeated hashing before introducing a security-sensitive cache. Cache duplicate metadata. Defer regex-query refactoring unless wider profiles demonstrate a real gain. |

Keep the existing single expensive workflow limit until lease and shared-state invariants are fixed. Adding processes or replicas now would increase exposure to concurrency defects. Recommended benchmark axes are rows, schema width, relationship candidates, date horizon and network latency, with exact-output comparison, RSS/temp-disk use and status-response latency. Avoid brittle wall-clock assertions in ordinary unit tests.

The existing tests are materially useful. The recurring blind spot is composition: direct helper tests cover approval rejection without the workflow cache; recovery tests replace a dead owner's fields without resuming a stale worker; success-only telemetry tests do not inspect exception exports; SQL/Python agreement does not prove that both use the right semantic classification.

Add a small deterministic boundary suite first. Use barriers for concurrency and exact synthetic canaries for sink checks. A later narrowly scoped [stateful property test](https://hypothesis.readthedocs.io/en/latest/stateful.html) can explore review/revoke/expire/resume/rerun/cancel/claim sequences. Whole-project coverage percentage is less useful here than proving those specific invariants. The existing 100% branch gate covers the reference metric module only.
